# DocxTool Integration Contract v1

`integration-contract-v1` is the stable, host-neutral boundary for reusing the
DocxTool recognition wheel from WPS, Microsoft Word, LibreOffice, or another
local editor.

This contract only covers recognition and text binding. It does not fetch the
active WPS document, create Word ranges, insert comments, modify formatting, save
files, or control an editor undo stack.

## Public Objects

- `SdkManifest`: text-free capability negotiation.
- `RecognitionRequest`: input options for `recognize_docx`.
- `RecognitionPlan`: source DOCX recognition output.
- `HostSnapshot`: local editor paragraph text snapshot.
- `HostSnapshotSummary`: text-free diagnostic summary, not bindable.
- `RecognitionBinding`: host-neutral paragraph and fragment binding output.
- `ValidationReport`: schema and semantic validation result.
- `SdkError`: stable error object for Python and CLI callers.

JSON Schema files are installed with the wheel under
`docxtool/resources/schemas/`. Python dataclasses are one implementation of the
schema, not the protocol authority.

## Versions

- Integration contract: `integration-contract-v1`
- SDK manifest schema: `sdk-manifest-v1`
- Recognition request schema: `recognition-request-v1`
- Recognition plan schema: `recognition-plan-v1`
- Host snapshot schema: `host-snapshot-v1`
- Recognition binding schema: `recognition-binding-v1`
- SDK error schema: `sdk-error-v1`
- Source locator: `source-locator-v2`
- Host text contract: `host-text-v1`
- Offset encoding: `utf16_code_unit`

Hosts must call `get_sdk_manifest()` or `docxtool-sdk manifest` before assuming
a wheel supports a specific schema or capability.

The manifest declares the binding scope. Version 2.0 binds only `main` story
paragraphs and excludes table paragraphs; host adapters must not infer header,
footer, comment, text frame, or table range support from the recognition output.

## Two Stages

Stage 1, recognition:

```python
from docxtool.sdk import RecognitionRequest, recognize_docx

plan = recognize_docx(
    "snapshot.docx",
    request=RecognitionRequest(processing_mode="structural"),
)
```

Stage 2, binding:

```python
from docxtool.sdk import bind_recognition_plan

binding = bind_recognition_plan(plan, host_snapshot)
```

The binding stage can run later, in another process, by loading `plan.to_dict()`
from JSON. It does not require the source DOCX again.

Every Mapping input follows this order before execution:

1. JSON Schema validation.
2. Cross-field semantic validation.
3. Dataclass deserialization.
4. Recognition or binding execution.

`validate_recognition_request`, `validate_recognition_plan`,
`validate_host_snapshot`, and `validate_recognition_binding` return
`ValidationReport` with `valid`, `errors`, and `warnings`. Each issue contains a
stable code, JSON path, severity, and allowlisted detail. `strict=False` permits
unknown non-critical extension fields as warnings; `strict=True` rejects unknown
fields and unsupported legacy upgrades.

## Stable IDs

`plan_id` is deterministic from source hash, protocol versions, recognition
engine, package version, locator version, host text contract, offset encoding,
recognition mode and request/config digest. It never contains a file path or
document text.

`block_id` is deterministic inside one plan. It is derived from `plan_id`,
`physical_group_id`, segment index, fragment hashes and semantic type.

`physical_group_id` groups multiple logical blocks split from the same DOCX
physical paragraph.

`snapshot_id` and `host_paragraph_id` are generated by the host. They only need
to be stable within one snapshot lifecycle.

Compatibility fields remain available for one migration period:

- `block_index`
- `source_paragraph_index`
- `host_paragraph_index`
- `range_start_utf16`
- `range_end_utf16`

New host adapters should prefer stable IDs and use indexes only as display or
diagnostic hints.

## Coordinates

Source spans belong to DOCX extracted paragraph text:

- `source_locator.raw_span`: source raw text UTF-16 code units.
- `source_locator.canonical_span`: source canonical text UTF-16 code units.
- `range_start_utf16` and `range_end_utf16`: compatibility aliases for source raw
  UTF-16 offsets.

Host spans belong to the supplied `HostSnapshot`:

- `host_target.raw_span`: host snapshot raw text UTF-16 code units.
- `host_target.canonical_span`: host snapshot canonical text UTF-16 code units.

None of these offsets are WPS Range, Office.js Range, VSTO Range, or COM Range
coordinates.

## Host Text v1

`HostSnapshot.paragraphs[].raw_text` is visible physical paragraph text. It must
not include an editor's implicit paragraph terminator. The SDK generates
canonical text internally:

- CRLF, CR, LF and vertical tab become LF.
- Tab and form feed remain explicit controls.
- NBSP and full-width space become normal space through NFKC.
- A trailing table-cell marker is excluded from canonical text and reported as a
  warning.
- All offsets are UTF-16 code units.

Hosts must not send precomputed canonical text as `raw_text`.

## Binding Status

- `confirmed`: raw text, canonical text, hashes, fragment spans and order match.
  The host may continue to real Range verification.
- `review`: canonical text matches but raw expression differs. Preview only.
- `unresolved`: missing, ambiguous, stale, unsupported or hash mismatch. Skip.

Recommended actions are fixed:

- `confirmed` -> `verify_host_range`
- `review` -> `preview_only`
- `unresolved` -> `skip`

`verify_host_range` does not mean "write immediately".

The field combinations are part of the protocol:

- `confirmed` must include a non-empty `host_paragraph_id`, raw/canonical host
  spans, paragraph and fragment hashes, and write preconditions.
- `review` must use `preview_only`.
- `unresolved` must use `skip` and must not carry executable host spans or
  preconditions.

`binding_id` changes when the snapshot, binding status, host paragraph, raw or
canonical span, fragment hash, or write precondition changes.

## Preconditions

Each confirmed block includes:

- `plan_id`
- `snapshot_id`
- `document_identity`
- `document_revision`
- `host_paragraph_id`
- `host_paragraph_raw_sha256`
- `host_paragraph_canonical_sha256`
- `raw_fragment_sha256`
- `canonical_fragment_sha256`
- `text_contract_version`
- `offset_encoding`

Before writing, a host adapter must re-read the current editor paragraph,
canonicalize it with `host-text-v1`, validate paragraph and fragment hashes,
create a real editor range, read the range text back, and only then apply
formatting.

## Privacy

`RecognitionPlan` is text-free by default and does not include source paths,
usernames, cookies, tokens, database paths or logs. `include_text` and
`include_raw_text` are explicit local-only opt-ins.

`HostSnapshot` necessarily contains current document text. It should stay in a
local memory or local IPC chain and must not be uploaded or written to ordinary
logs.

`HostSnapshotSummary` intentionally omits `raw_text` and cannot be passed to the
binding API. It is only for UI diagnostics and logging-safe counts.

## Errors

Python exceptions and CLI errors share `sdk-error-v1`. Stable codes include:

- `INVALID_RECOGNITION_REQUEST`
- `INVALID_RECOGNITION_PLAN`
- `INVALID_HOST_SNAPSHOT`
- `INVALID_RECOGNITION_BINDING`
- `UNSUPPORTED_INTEGRATION_CONTRACT`
- `UNSUPPORTED_SCHEMA_VERSION`
- `UNSUPPORTED_HOST_TEXT_CONTRACT`
- `UNSUPPORTED_OFFSET_ENCODING`
- `SOURCE_DOCUMENT_CHANGED`
- `SOURCE_LOCATOR_NOT_CONFIRMED`
- `PHYSICAL_PARAGRAPH_UNMATCHED`
- `SOURCE_OCCURRENCE_AMBIGUOUS`
- `SOURCE_TEXT_HASH_MISMATCH`
- `SEGMENT_GROUP_INCOMPLETE`

Error details must use IDs, indexes, hashes and JSON paths. They must not include
document text, absolute local paths or tracebacks. Unknown exceptions are mapped
to stable SDK error envelopes before they reach ordinary callers.
