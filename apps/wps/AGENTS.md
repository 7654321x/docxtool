# WPS App Rules

本文件只约束 `apps/wps/`。

1. WPS 是 DocxTool 的外围应用，不是第二套文档引擎。
2. `apps/wps` 可以调用 `src/docxtool` 的公开能力；`src/docxtool` 不得依赖、导入或判断 WPS。
3. WPS 专属代码只负责 Ribbon、任务窗格、宿主生命周期、本地控制、预览交互和诊断。
4. 禁止在 WPS 目录复制识别规则、规范化规则、格式 profile、编号规则、字体规则或正式排版 Engine。
5. 正式排版必须走 `DocxImporter -> Recognition(authoritative) -> Normalization -> Engine -> validate_docx_integrity`。
6. 正式排版失败时不得 fallback 到 WPS API 第二套格式写入；保持原文件不变并暴露真实错误。
7. 排版必须先写临时 DOCX；WPS 关闭原文档后才允许事务替换，重新打开成功后再删除备份。事务状态必须写入本地 runtime journal，Control Server 重启时恢复未完成替换。
8. 预览默认只读，不写正式格式。需要文档批注时应作为独立宿主交互能力实现，不改变识别/排版规则。
9. 预览定位必须使用 `HostSnapshot -> bind_recognition_plan()`。禁止直接把 DOCX `physical_paragraph_index` 当作 WPS `Paragraphs.Item()` 下标，也禁止在 WPS 端重新实现 source locator、重复段落消歧或 canonical text 绑定。
10. 预览批注允许使用 SDK Binder 返回的 `confirmed + verify_host_range` 和 `review + preview_only`；两者创建和读回 Range 时都必须再次验证 Binder precondition 中的段落 raw hash 与 fragment raw hash，`review` 批注必须明确提示人工复核且不得用于正式格式写入。`unresolved + skip` 始终禁止创建 Range 或批注。
11. 调用识别或正式排版前必须等待 WPS `Document.Save()` 真正完成；不能在 `Save()` 返回后立即让 Python 读取磁盘文件。
12. 预览批注跟踪状态按文档 identity 隔离，切换文档不得覆盖另一文档的 preview session。
13. Python 日志复用 DocxTool `docx_tool` logger、`LOG_FORMAT`、文档 context log；JS 日志通过本地 Control Server 汇入相同格式。
14. 日志不得记录正文、完整绝对路径、session token 或完整文件哈希；日志文件名使用通用 `document` 前缀，路径使用脱敏 `file_id`。为区分 WPS 多文档窗口，业务命令日志允许记录 `Application.ActiveDocument.Name` 产生的 `document_name`，但不得记录 `FullName` 或从路径推导额外目录信息。
15. Windows 显式命令使用 PowerShell 7：`pwsh -NoProfile -Command "..."`。
16. 修改后至少运行 `python apps/wps/main.py verify`、`python -m pytest apps/wps/tests -q`、JavaScript 语法检查和 XML/JSON 解析；这些门禁必须进入仓库 CI。没有真实 WPS 验证时不得声称真实宿主 PASS。
17. WPS 业务命令统一经 Control Server 的单个 `CommandMonitor` 线程串行执行；HTTP 日志接收和健康检查不占用业务命令槽。WPS 的 `Application`、`Document`、`Range` 和 `Comments` 操作只在 Host Runtime 中执行，Python 监控线程不得直接调用 WPS 对象。
18. Launcher 默认只启动 Control Server 和本机插件静态服务，并更新当前项目的 `publish.xml` 注册；不得自动拉起、关闭或轮询 WPS 进程。用户在服务就绪后自行打开 WPS 文字，由 WPS 按注册 URL 加载插件。插件网页服务固定使用 `127.0.0.1:3889`，保持 WPS 信任来源稳定，并对全部资源发送 `no-store` 响应；端口占用时必须直接失败，不得回退到随机端口。启动器只能更新 `docxtool-wps-app` 条目，必须保留其他加载项；Control 日志和事务产物继续位于插件源码目录之外。修改后运行 `apps/wps/tests/test_wps_app.py` 的后台启动、静态服务和注册保留测试。
19. Host 与 TaskPane 的业务通信统一通过 Control Server `HostBridge` 单槽长请求完成：Host 注册 generation 后等待命令，TaskPane 按 revision 等待状态。命令入槽必须立即递增 revision，唤醒 TaskPane 已存在的 25 秒状态等待，使未领取命令进入 5 秒 ACK 等待；不得只通知 Condition 而保持 revision 不变。两端不得使用业务 `setInterval` 或 PluginStorage 命令/状态槽；PluginStorage 只保留任务窗格 ID、页面版本和按文档隔离的预览元数据。忙碌、Host 未就绪、generation 过期、协议无效和字段缺失必须分别使用独立事件与错误码。
20. 日志必须在真实失败源头记录具体事件，顶层 `host.command.failed`、`monitor.command.failed` 和 Control 请求失败只作关联汇总。保存调用、保存等待、文档路径、HostSnapshot、SDK Binding、Range 各项前置条件、批注创建/回滚、排版阶段和事务状态转换不得用同一个通用错误事件替代。
21. Python 与 JS 日志统一只允许阶段、状态、耗时、计数、稳定错误码、脱敏短 ID，以及第 14 条限定的 `document_name`。正文、绝对路径、Token、Authorization、原始快照、Range 文字、完整哈希和 traceback 不得进入日志；`/v1/log` 及其 OPTIONS 不生成普通请求/access 日志，日志传输失败只在当前 JS 上下文输出一次脱敏错误。
22. `OnAddinLoad` 是 Host Runtime 的首选启动入口；若 WPS 复用无窗口后台宿主而未触发该回调，首次点击“状态面板”必须在 WPS 主线程中幂等调用同一个 `HostRuntime.start()` 后再创建 TaskPane。WPS 创建或复用任务窗格后可能重新加载主 Bootstrap，新 Bootstrap 完成时必须再次调用同一个幂等入口，确保当前页面上下文只有一个 Host 长请求。新的 Host generation 必须立即使旧 Host、旧命令和旧 TaskPane 状态等待失效；25 秒正常超时不得记录为错误，网络或协议失败必须停止等待链且不得回退到 PluginStorage 轮询。必须记录 `bootstrap.host_start.enter/completed/failed` 和 Bridge 注册、命令、状态、停止事件。`CreateTaskPane` 按锁定版本官方模板只传 URL。该场景必须运行 `node --test apps/wps/tests/wps-runtime.test.mjs`。
23. 触发场景：WPS“一键排版”没有传入格式配置时，必须使用 `structural` 处理并默认启用现有 Core 序号规范和安全标点；已识别的一至四级标题按层级重建可见序号，URL、邮箱、版本号等技术片段由 Core 安全标点引擎保护，不得在 WPS 端复制编号或标点算法。调用方显式传入配置时保持其 `numbering.enabled` 和 `punctuation.enabled` 原意。配置完成日志必须记录实际处理模式、编号开关和安全标点开关。修改后运行 `apps/wps/tests/test_wps_app.py` 中的一键排版编号、安全标点回归，以及 `tests/test_processing_flags.py tests/test_punctuation_engine.py`。
24. 触发场景：正式排版替换当前唯一文档时，不能先关闭该文档再依赖同一 Host 页面调用 `Documents.Open()`；关闭唯一文档会销毁加载项上下文。必须先用 `Document.SaveAs2()` 切换到唯一桥接 DOCX，由桥接文档保持 Host，提交源文件替换并通过 `Documents.Open()` 重开源文档后，再关闭桥接文档并用 `FileSystem.unlinkSync()` 删除。失败回滚同样必须在源文档恢复后清理桥接文件。修改后运行 `node --test apps/wps/tests/wps-runtime.test.mjs`。
25. WPS `customUI` 的 `<tab>` 不支持 `onAction`，不能依赖点击自定义页签直接执行代码。需要精简 Ribbon 时保留一个明确的 TaskPane `<button onAction>` 入口，预览、排版、清除和检测等业务操作放在侧边栏中；不得向 `<tab>` 添加非官方点击回调。修改后解析 `ribbon.xml` 并运行 WPS JS Runtime 测试。
26. 触发场景：WPS 当前活动文档是旧版 `.doc` 或 `.wps` 时，`预览排版`和`一键排版`必须在同一个 Host 前置入口中静默永久升级为同名 `.docx`；`本机检测`不得触发升级，`清除预览`在旧格式上直接成功返回 0。升级只允许由 WPS Host 对隐藏临时文件调用一次 `Document.SaveAs2(path, 12)`；预览原样发布转换结果后继续现有 SDK 识别与 Binding，排版复用该转换桥接文件进入现有 Core 事务。同名 `.docx` 已存在时必须在转换前停止且不得覆盖；旧源内容在新 DOCX 重开成功前必须保留于事务备份，任一失败都恢复旧源文件。不得只修改扩展名，不得在 Python 中解析旧格式，也不得建立第二套识别或排版链。日志按 `document.format.*`、`document.upgrade.*` 分阶段记录，修改后运行 `apps/wps/tests/test_wps_app.py` 的 legacy upgrade 测试及 `node --test apps/wps/tests/wps-runtime.test.mjs`。
27. 触发场景：PyCharm 将 `stderr` 整体显示为红色时，统一控制台日志必须将 `DEBUG/INFO` 写入 `stdout`，将 `WARNING/ERROR/CRITICAL` 写入 `stderr`，且每条日志只能进入一个控制台流。不得在日志正文或文件日志中加入 ANSI 颜色码；滚动文件和文档上下文日志继续保存全部等级的纯文本。修改后运行 `tests/test_style_config_features.py` 和 `apps/wps/tests/test_wps_app.py` 的日志测试。
28. 识别预览批注是面向用户的结果提示，统一使用“识别格式：类型；置信度……”文案；不得展示内部 Engine、SDK 或处理链实现说明。修改后运行 `node --test apps/wps/tests/wps-runtime.test.mjs`。
29. 触发场景：WPS 内嵌任务窗格滚动时，`position: sticky` 和 `position: fixed` 都可能随宿主页面滚动失效。任务窗格页面自身禁止滚动，顶部操作区保留在正常布局中，仅允许下方 `main` 内容区滚动。WPS 会在页面脚本初始化后恢复历史根滚动位置，因此必须在初始化时归零，并在页面 `load` 完成后的下一轮事件中再归零一次；日志分别记录阶段及根页面、body、内容区滚动值。WPS 官方 `GetTaskPane(id)` 只复用已有网页实例，页面结构升级时应通过独立页面版本识别旧实例，隐藏后再用带版本参数的 `CreateTaskPane(url)` 重建一次，版本一致时继续复用。修改后运行任务窗格加载后滚动、版本替换和 WPS JS Runtime 测试。
30. 触发场景：首次打开 TaskPane 时网页内部 header 几何、滚动和事件循环均正常，但 WPS 原生窗格仍遮挡顶部并占用文档操作焦点。创建时必须先按官方契约设置右侧 `DockPosition` 和目标 `Width`，再设置 `Visible=true`；显示后调用当前 `Document.Activate()` 与 `Document.ActiveWindow.Activate()` 将焦点交还文档。不得依赖一键排版重开文档触发原生重排，也不得用 CSS 位移掩盖宿主裁剪。修改后运行 `node --test apps/wps/tests/wps-runtime.test.mjs`，并在真实 WPS 中首次打开侧边栏验证顶部完整和文档可立即操作。
31. 触发场景：TaskPane 网页内部报告 header 可见，但真实 WPS 画面仍裁掉顶部，且一键排版重开文档后恢复。不得仅凭一次属性赋值或网页几何推断根因；必须分别记录 `DockPosition/Width/Visible` 的写入前值、请求值、立即读回值和 0/100/500/1000ms 延时读回，并在一键排版的预览清理、桥接 `SaveAs2`、事务提交、目标 `Documents.Open`、目标激活、桥接关闭及 finalize 前后采集相同窗格和活动文档快照。TaskPane 同时记录屏幕坐标、DPI、网页可视区、header/content 几何及 pagehide/beforeunload/unload，直到真实日志证明首次打开与重开后的第一个差异点。
32. 触发场景：首次创建 TaskPane 时，`Visible` 和 `DockPosition` 写入及读回都可能成功，但 WPS 原生窗格坐标仍停留在 Ribbon 区域；网页 header 几何和文档焦点状态都不能证明宿主已重排。真实日志确认一键排版是在第二个文档关闭后首次触发原生 resize，因此 TaskPane 在首次 Host READY 与 `load_settled` 同时成立后，经现有 Bridge 单次提交 `panel_ready`；Host 只执行 `Documents.Add() → 原文档 Activate() → 临时文档 Close(0)` 并等待布局稳定，不保存临时文档、不调用 Engine，也不再依赖浮动/右停靠或 `ActiveWindow.Activate()`。页面版本变化时替换旧实例。修改后运行 `node --test apps/wps/tests/wps-runtime.test.mjs`，并在真实 WPS 首次打开侧边栏验证 `screenY/innerHeight` 发生原生 resize、顶部完整且临时文档已关闭。
33. 触发场景：自定义 Ribbon 大按钮没有图标时，使用 WPS 官方 `getImage` 回调返回仓库内 SVG；图标采用 24×24 `viewBox`、透明背景、深灰主体和 WPS 蓝强调，并加入启动校验与发布清单。`JsApiShowWebDebugger` 生成的“打开JS调试器”是 WPS 原生调试入口，不属于项目 `ribbon.xml`，没有官方图标覆盖接口；不得复制按钮或猜测未公开的调试器调用 API。
34. 触发场景：TaskPane 内直接调用 `Document.Activate()` 和 `ActiveWindow.Activate()` 可能记录成功但没有可见交互结果，不保留“返回文档”这类无效按钮。Host/Bridge 状态协议继续使用 `READY/RUNNING/PASS/FAIL` 等稳定大写值，任务窗格只在显示层转为 `Ready/Running/Pass/Fail`；不得改写协议、日志或状态判断。
35. 触发场景：WPS 重载 Bootstrap 时，`Application.ribbonUI` 可能是不可重新定义的宿主代理属性。`OnAddinLoad` 必须把 WPS 传入的 Ribbon UI 保存在 Host Runtime 自有变量中，不得写回 `Application`；所有 Ribbon 回调按 `wpsjs 2.2.3` 官方模板返回布尔值或字符串。修改后运行 `node --test apps/wps/tests/wps-runtime.test.mjs`。
36. 触发场景：一键排版已在本机完成，但公网结果暂时不可达。主命令状态必须继续保持 `PASS/FAIL` 的本地真实结果，结果先进入当前进程的内存补报队列，并通过 `result_sync_status=pending` 与账号摘要中的 `pending_result_count` 显示“结果尚未同步”；下一次心跳恢复后补报，数量归零时 TaskPane 自动清除提示。公网业务拒绝表示服务器可达，只有 `PublicApiError.network=True` 才将客户端标记为离线。内存队列不持久化，Launcher 退出时记录数量并清空；不得把同步失败改判为文档事务失败，也不得覆盖 HostBridge 的原始错误。修改后运行 `apps/wps/tests/test_launcher_auth.py`、`apps/wps/tests/test_host_bridge.py` 和 `node --test apps/wps/tests/wps-runtime.test.mjs`。
37. 触发场景：公网授权返回完整排版配置时，配置只能由本机 Control 验证后保存在授权上下文并注入 Engine；HostBridge 只向 Host 发送同一 `request_id` 和 `config_version`，Host 调用排版接口不得回传 `format_config`，请求体中的伪造配置不得覆盖授权配置。每个授权只能绑定一个 `apply` 事务，事务同时绑定创建时的请求编号和 `preview/apply` 用途；`commit/finalize/rollback` 必须使用同一请求编号，`preview` 不得调用 Engine。Host 终态必须先验证 context 和 generation，再消费授权并加入补报队列；Host 更换只为被替换的 `apply` 加入一次失败结果。TaskPane 账号、网络、功能可用性和待补报数量统一从 `/v1/bridge/state/wait` 响应更新，不得增加 `/v1/account` 轮询或一次性快照。修改后运行 WPS Python、HostBridge 和 Node Runtime 测试。
38. 触发场景：登录窗口固定高度导致注册字段把“注册并登录”按钮挤出客户区。登录和注册使用同一独立窗口的两个视图，窗口必须在视图切换后根据 `winfo_reqheight()` 重新计算高度并居中，不得用固定高度假设 DPI；提交逻辑提取为无 UI 依赖函数，登录只调用 `api.login()`，注册只调用 `api.register()`。WPS 插件只使用唯一登录账号，不设置显示名称；新接口、账号摘要、TaskPane 和 WPS 管理后台不得读写或展示 `display_name`，旧 SQLite 遗留列仅为兼容保留且不得执行删列迁移。网页版普通用户体系不适用本条。修改后运行登录窗口、账号存储、WPS Server、管理后台和 Node Runtime 测试。
39. 触发场景：登录输入框使用带水平内边距的边框容器时，容器背景会在输入框两端露出灰色竖条。输入框统一使用完整圆角描边，不放账号前后缀装饰；密码和确认密码在右侧提供可点击的眼睛按钮，并直接切换 Tk Entry 的 `show` 属性。顶部只保留 DocxTool 品牌标识，不放宣传文案。修改后运行 `apps/wps/tests/test_login_window.py`，并在真实 Windows 窗口检查登录、注册和密码显示切换。
40. 触发场景：`/v1/format/prepare` 已创建事务，但响应在 Host 取得 `operation_id` 前中断时，Host 无法通过原有 operation ID 路由回滚，后续排版会持续返回 `WPS_FORMAT_BUSY`。Host 发布同一 `request_id` 的 `apply/FAIL` 终态时，Control Server 必须按完整请求编号精确查找并调用既有事务回滚；`PASS`、其他命令和其他请求不得触发清理。找不到事务表示 Host 已完成回滚，可继续记录失败结果；真实回滚失败必须保留授权与原异常，不得报告已清理。修改后运行 `apps/wps/tests/test_host_bridge.py` 中的 apply 终态回归和 `apps/wps/tests/test_wps_app.py` 的事务 busy 回归。
41. 触发场景：Control Server 启动时发现 `committed` 事务的源文件已匹配排版结果，而备份和临时文件均已缺失，说明排版结果已经生效且没有可恢复备份。此时直接清理旧事务 journal 并继续启动，不得因 `WPS_TRANSACTION_RECOVERY_REQUIRED` 阻塞服务，也不得改写当前文档。其他文件状态仍按既有事务校验处理。
